# AdPulse

Next.js 16 (App Router) + React 19 ad-analytics dashboard, with an OpenRouter-powered AI chat. **Companion app to Atlas (ai-page-generator)**: it shares Atlas's Clerk instance for auth (one login for both apps) and Atlas's Neon Postgres database (`atlas-db`) for data — AdPulse owns the dedicated `adpulse` Postgres schema there; Atlas owns `public`. Production domain: adpulse.relevantaudience.com (same root domain as Atlas, so the Clerk session cookie is shared and Atlas users arrive already signed in).

## Commands

- `npm run dev` — dev server on :3000
- `npm run check` — **the verification command**: `typecheck` then `lint`
- `npm run typecheck` / `npm run lint` — the two halves individually
- `npm run start` — serve the built app

**`npm run build` is FORBIDDEN — never run it.** `next build` and `next dev` share the `.next/` directory, so a build (especially a failed one) writes production artifacts over the dev server's state and leaves it serving 404 for *every* route until `.next/` is wiped. Builds are the user's to run, themselves, with the dev server stopped. Do not run it "just to check", and never offer it as a verification step.

**There is no test suite and no test runner installed.** Do not attempt `vitest`/`jest`. Verification for every change is `npm run check` — nothing else. Expect ~135 pre-existing eslint warnings, all inside `.claude/skills/**`; the bar is zero errors and no new warnings in `src/`.

`typecheck` runs `tsc -p tsconfig.check.json`, a copy of `tsconfig.json` that excludes `.next/`. The default config feeds Next's generated route-type validators (`.next/dev/types/validator.ts`) to `tsc`, and the running dev server rewrites those constantly — a plain `npx tsc --noEmit` can fail on a syntax error inside half-written generated code that has nothing to do with your change. Editors keep using `tsconfig.json`, so route-type checking is not lost where it helps.

**Never delete `.next/` on this machine without warning the user first.** Turbopack's cache there holds the already-downloaded `Stack Sans Text` webfont. WSL2 here has broken IPv6 (DNS returns an AAAA record, the route black-holes), and Turbopack's Rust fetcher does not fall back to IPv4 the way `curl` does — so a cold `.next/` makes `next/font/google` fail to fetch from `fonts.gstatic.com`, and `src/app/layout.tsx` then throws module-not-found, 500ing every page. `curl` succeeding against Google Fonts proves nothing; it uses Happy Eyeballs. Recovery is to restore `.next/dev/cache` from a backup, so back the directory up (move, don't delete) before touching it.

## Architecture

- **UI is file-based `[clientId]` routing.** Client-scoped views live under `src/app/[clientId]/<view>` (dashboard, pacing, funnel, attribution, health, creatives, alerts, compare, reports, team) with the shared shell/guard in `src/app/[clientId]/layout.tsx`; `/` serves public shared reports (`?share=`) and redirects signed-in users to their first client. The only other page is `/login` (Clerk `<SignIn />`, catch-all segment).
- **Auth & multi-tenancy (shared Atlas Clerk).** `src/proxy.ts` (Next 16's replacement for `middleware.ts`) wraps `clerkMiddleware` and gates everything except `/login`, `/` with `?share=`, and `GET /api/reports/share`; unauthenticated API calls get 401, pages redirect to `/login` (Clerk's `<SignIn />` in a catch-all route). Identity = the shared Clerk session; authorization = Atlas's `public.user_roles` row for that Clerk user, mapped onto `AppRole` by `src/lib/auth/atlas-roles.ts` (admin → agency_admin; manager/account_manager/head_account_manager → agency_member; client → client_user; every other Atlas role → NO access). A `client_user` sees only AdPulse clients whose `clients.atlas_project_id` matches one of their Atlas project assignments (`public.project_users`). Server-side authorization lives in `src/lib/auth/session.ts` (`getAuthContext()`) and `src/lib/auth/guard.ts` (`requireUser`/`requireClientAccess`/`requireAgencyRole`/`allowedClientIds`); **every API route must call the guard before any DB work** because `clientId` is caller-supplied and authorization is app-layer. Role-gated UI reads `useCurrentUser()` (`/api/me`) with helpers in `src/lib/auth/roles.ts`. **AdPulse stores no user tables and manages no users** — invites, roles, and project assignments happen in Atlas; `/api/users` + the `team` view are a read-only directory derived from the Atlas tables (read-only Drizzle models in `src/lib/db/atlas-schema.ts` — never write to or migrate `public` from this repo).
- **The `dashboard` view is a customizable widget grid** (`src/components/dashboard/customizable-dashboard.tsx`) on **react-grid-layout 2.x**. Widgets are declared in a registry (`src/lib/dashboard/widget-registry.tsx`) — each has a `Render` component (reusing existing hooks), optional `ConfigForm`, default size/config. Edit state (draft/dirty/add/remove/resize) lives in `src/store/dashboard-store.ts`; layouts persist per client via `useDashboard`/`useSaveDashboard` → `/api/dashboards` (localStorage is an offline cache). `src/lib/dashboard/default-preset.ts` mirrors the classic fixed layout; it is now only the SEED for the master dashboard template's row (created lazily on first read) — what an unsaved client actually renders is that master template. **Per-widget filters + custom widgets:** any widget may carry `config.filters = { platforms?, campaignIds? }` (`src/lib/dashboard/filters.ts`, `useWidgetScope`, shared `WidgetFiltersForm`; empty platforms = follow the page selector); the `custom` widget type (`src/lib/dashboard/custom-widget.ts` is the contract: visualization number/line/bar/table, 1..N metrics, groupBy none/platform/campaign, timeBucket none/day/week, top-N sort) is fed by `runMetricQuery` (`src/lib/data/metric-query.ts`, SQL GROUP BY + TS ratios) via `/api/metrics?action=query`; dashboards PUT validates every widget config with `src/lib/dashboard/widget-schemas.ts` (strict for `custom`). **Saved widget library** (`saved_widgets`, agency-wide, `/api/saved-widgets` + `src/lib/data/saved-widgets.ts`, `useSavedWidgets`): a widget instance may carry `savedWidgetId` — the library row then owns the config (dashboards store only the pointer, reads hydrate it back, so one edit changes every view that links it), with the transient PUT flag `syncToLibrary` writing an edit back to the library and deletes detaching (config materialized inline) first — in views *and* templates. **Dashboard templates** (`dashboard_templates`, agency-wide, `/api/templates` + `src/lib/data/templates.ts`, `useTemplates`): a named snapshot of one view's layouts + stored-form widgets, not tied to any client — `POST /api/dashboards {clientId, name, fromTemplateId}` stamps it onto any client, and linked `savedWidgetId` widgets stay linked so "agreed metric" widgets keep syncing. Templates are copies, not live mirrors: editing the source view (or deleting the template) never touches what was stamped from it. **The master template** is one flagged row (`dashboard_templates.is_master`, at most one via a partial unique index): it is what a client with no saved view renders (`getDefaultDashboard`) and what `POST /api/dashboards {clientId, name, fromMaster: true}` stamps. `getMasterTemplate()` creates it from `buildDefaultDashboard()` the first time it is asked for. Template CONTENT is editable through `PUT /api/templates {id, layouts, widgets}` (same widget resolution + one-transaction library sync as the dashboards PUT); the UI only exposes it for the master, and the master cannot be deleted (409). **RGL 2.x ≠ the tutorials/1.x:** it self-measures via `useContainerWidth` (no `WidthProvider`), uses config objects (`dragConfig`/`resizeConfig`) instead of flat `isDraggable`/`draggableHandle` props, ships its own types (do **not** install `@types/react-grid-layout`, which is the 1.x API), and drops `findDOMNode` (which is why 1.x would crash under React 19).
- **Report builder.** Block-based reports mirror the dashboard system one level over: a **report layout** (`report_layouts`, `src/lib/data/report-layouts.ts`, `/api/report-layouts`) is a client's editable block structure — same grid/widget vocabulary and same stored form as a dashboard view, so a `savedWidgetId` link syncs across dashboards *and* reports — and a **report template** (`report_templates`, `src/lib/data/report-templates.ts`, `/api/report-templates`) is an agency-wide snapshot of one layout, stamped onto any client. Layouts and templates are agency-internal: a client_user only ever sees the *generated* report in the existing reports list. **Generating** a report from a layout is live: `POST /api/reports {clientId, fromReportLayoutId, title, dateRange}` (agency-only) freezes the layout through `buildReportLayoutSnapshot` into `reports.view_snapshot` with `pageStyle: "document"`, and the renderer draws it as a centred page. Two report-only block types exist — `cover` (client name + period frozen at build time) and `ai-summary` (prose written once via OpenRouter in `src/lib/reports/ai-summary.ts`, with a deterministic fallback and `generated: false` whenever the key, the network or the 30s timeout says no — a report is never blocked by the model). Which grid a widget type may live on is `widgetSurface()` in `src/lib/dashboard/types.ts`; `resolveWidgets(widgets, surface)` enforces it, so the dashboards PUT rejects report-only blocks and the report-layouts PUT accepts them. **The UI is agency-only and lives in the reports view** (`src/components/dashboard/reports-view.tsx`): a "Report layouts" panel (`src/components/reports/report-layouts-panel.tsx` — new/rename/duplicate/delete/save-as-template, driven by `src/hooks/use-report-layouts.ts` + `use-report-templates.ts`; the `TemplatePicker` takes `kind="report"`) swaps the view for a block editor (`src/components/reports/report-layout-editor.tsx` — the dashboard's RGL wiring on an 880px document-width page, `WidgetCatalogDialog surface="report"`) and generates through `src/components/reports/generate-report-dialog.tsx`. Grid edit state is shared: `src/store/grid-edit-store.ts` holds the generic draft/dirty/add/remove/resize slice, and `useDashboardStore` (plus its per-client view selection) and `useReportLayoutStore` are its two instances. The widget-linkage rules are shared, not forked: `resolveWidgets` (`src/lib/data/saved-widgets.ts`) and `gridLayoutsSchema`/`MAX_WIDGETS` (`src/lib/dashboard/widget-schemas.ts`) are used by both the dashboards and report-layouts PUTs. **The master report template** mirrors the dashboard one: a flagged row (`report_templates.is_master`, partial unique index), created lazily by `getMasterReportTemplate()` from `src/lib/dashboard/default-report-preset.ts` (cover → AI summary → KPI row → trend → channels/movers → campaign table; no demo-only blocks), stamped by `POST /api/report-layouts {clientId, name, fromMaster: true}`, content-editable via `PUT /api/report-templates`, previewable against a client's data with `GET /api/report-templates?action=preview` (`buildReportTemplateSnapshot`), and undeletable (409).
- **Data layer:** `src/lib/data/queries.ts` queries Postgres via **Drizzle** (`src/lib/db`). `src/lib/data/health-score.ts` and `attribution.ts` derive analytics on top of `getMetrics` (attribution also reads `attribution_journeys`/`customer_cohorts`); `src/lib/data/dashboards.ts` reads/writes the `dashboards` table. These are called from API routes, not Server Components.
- **API routes** (`src/app/api/*`): `metrics` (GET, multi-action via `?action=`; `query` = grouped aggregation for custom widgets; all metric actions accept `platforms`/`campaignIds` comma lists), `attribution` (GET, `?action=overview|attribution|cohorts` — revenue/ROAS, multi-touch attribution, LTV cohorts), `dashboards` (GET by client/view + POST create view — blank, `duplicateFromId`, `fromTemplateId` or `fromMaster` + PATCH rename/publish/set-default + DELETE + PUT upsert of a view's layout), `saved-widgets` (GET list + `?action=usage&id=` + POST/PATCH/DELETE — the agency-wide widget library; usage and DELETE's detach cover dashboard views, dashboard templates, report layouts and report templates — all four store the same `savedWidgetId` pointer), `templates` (GET list + `?action=master` for the master's full content + POST snapshot-from-view + PATCH name/description + PUT content save + DELETE, which refuses the master with 409 — agency-wide dashboard templates), `report-layouts` (GET `?action=list` or `?id=` + POST create blank/duplicate/from-template/`fromMaster` + PATCH rename + DELETE + PUT upsert — the report builder's per-client layouts; **agency-only on every verb, GET included**, since layouts are internal), `report-templates` (GET list + `?action=master` + `?action=preview&id=&clientId=&start=&end=` + POST snapshot-from-layout + PATCH name/description + PUT content save + DELETE, which refuses the master with 409 — agency-wide report templates), `chat` (POST, SSE stream), `clients`, `campaigns`, `reports` (GET list + POST; POST takes the classic `{clientId, clientName, startDate, endDate}` payload **or** a **view report** `{clientId, fromDashboardId, title, dateRange}` — the latter runs `buildViewSnapshot` (`src/lib/reports/build-view-snapshot.ts`) to compute every widget of a saved dashboard view once and freeze layout + inlined config + data into `reports.view_snapshot`, so the report and its share link keep rendering the same numbers forever; `src/components/reports/view-report.tsx` draws that snapshot read-only on a plain CSS grid with no data hooks, reusing the widgets' extracted presentational halves — `custom-viz.tsx`, `FunnelStages`, `HealthGaugeReadout`, `RevenueRoasReadout`, `AttributionMiniChart`, `LtvCacReadout`. Classic reports are untouched: they keep `view_snapshot` NULL and the PDF/PPTX export path, which view reports deliberately do not have), `reports/share` (share links now carry `share_expires_at`; POST accepts `expiresInDays`; GET returns `viewSnapshot` too, only after the token/expiry/password checks pass, and `/?share=` branches on it), `report-schedules`, `alerts`, `creatives`, `creatives/generate`, `seed`, `me` (current user + profile), `users` (admin-only READ-ONLY team directory derived from Atlas — no CRUD, no invites). All routes are authorization-guarded (see Auth above): client-scoped reads check membership; alerts/report-schedules/creatives-generate/dashboards writes/saved-widgets writes/templates/reports-share-POST are agency-only, as is the **view-report POST** (it snapshots a whole view, including internal ones — a client_user may read the resulting report but never create one, and their `GET /api/reports` has `view_snapshot.sourceDashboardId` stripped); seed and users are agency_admin-only; report-layouts and report-templates are agency-only on every verb; reports/share GET is public (token + password).
- **Mock data + adapters:** `src/lib/mock-data/{google,meta,tiktok}-ads.ts` generate fake data; `src/lib/adapters/*` normalize each platform into the unified schema. Used only by the seed route.
- **Database types are hand-written** in `src/lib/types/database.ts` (nothing generates them). All AdPulse tables live in the `adpulse` schema of the shared project. Tables: `clients` (incl. `is_demo` — demo/seed clients keep showcase-only features — and `atlas_project_id`, the link to Atlas's `public.projects` that drives client_user access), `campaign_performance` (unified facts; `conversions` is **numeric** — Google DDA credit is fractional; `revenue` is **nullable** — NULL = value tracking not configured; `currency` per row; **no stored ctr/cpc/cpm** — ratios are computed in the `getMetrics` projection; partial unique index `(ad_account_id, campaign_id, date) WHERE ad_account_id IS NOT NULL` is the ingestion upsert target), `ad_accounts` (connected platform ad accounts — currency/timezone/Windsor mapping anchor), `raw_windsor_rows` (verbatim ingestion landing layer), `conversion_mappings` (per-account "which platform events = conversions/revenue"), `campaigns` (SCD-lite campaign dimension — status/objective/type are open platform enums, deliberately no CHECKs), `campaign_budgets`, `reports` (incl. `share_token`/`share_password_hash`/`share_expires_at`, plus `view_snapshot` jsonb — NULL = a classic narrative report, set = a frozen dashboard-view report), `chat_sessions`, `chat_messages`, `ad_creatives`, `alert_rules`, `alert_history`, `report_schedules`, `attribution_journeys` (cross-platform conversion paths — **demo-only, no real data source**), `customer_cohorts` (LTV/retention — **demo-only**), `dashboards` (per-client customizable dashboard **views** — many named views per client: `layouts`/`widgets` JSON plus `visibility` `'internal'|'client'` (published views are the only ones a client_user sees) and `is_default`, at most one per client via the partial unique index `(client_id) WHERE is_default`), `saved_widgets` (agency-wide library of reusable widgets — `name` unique on `lower(name)`, `widget_type` + `config` JSON; dashboard views reference a row by id and store no inline config), `dashboard_templates` (agency-wide whole-view snapshots — `name` unique on `lower(name)`, `description`, `layouts`/`widgets` JSON in stored form, plus `is_master` with a partial unique index `(is_master) WHERE is_master` so at most one row is the master; not client-scoped, used to create a view for any client), `report_layouts` (per-client **report** layouts for the report builder — the same `layouts`/`widgets` JSON and stored form as `dashboards`, unique on `(client_id, name)`, but agency-internal: no `visibility`, no `is_default`), `report_templates` (agency-wide report-layout snapshots — mirrors `dashboard_templates` exactly, `is_master` and its partial unique index included). There are NO user tables — roles/membership live in Atlas's `public.user_roles`/`public.project_users`. Update this file when the schema changes.
- **Windsor ingestion**: real ad data comes from Windsor.ai (`WINDSOR_API_KEY` in `.env.local`; Meta (4 accounts) and Google Ads (5 accounts) connected, TikTok absent). Background in `docs/data-ingestion-strategy.md` and `docs/schema-v2-assessment.md` (the phase plan there is superseded). **Meta + Google are live:** `src/lib/windsor/sync.ts` is a generic pipeline (`syncPlatform(platform)`) driven by per-platform adapters in `adapter.ts` (`meta.ts` = `facebook` connector, `google.ts` = `google_ads`): pull → land (`raw_windsor_rows`) → mapping-driven normalize (`conversion_mappings`, pure function of the landing layer — re-mapping never needs a re-pull) → upsert facts + `campaigns` dim (Google writes `campaign_type` = SEARCH/PERFORMANCE_MAX). Google mapping `event_key` = the Windsor field name; defaults are `conversions` (primary conversion actions only, fractional) and `conversions_value` — `all_conversions` is landed but deliberately unused. Account timezone is stored from Windsor (`account_timezone` Meta / `account_time_zone` Google; null rows are backfilled on sync). `POST /api/sync {connector: "meta"|"google", days?}` (agency_admin; auto window: 28d Meta / 30d Google incremental, 90d first-run; new Windsor accounts auto-create a real client (1 account = 1 client) + default mappings). Real clients are `is_demo=false`; attribution/creatives views + attribution widgets are demo-gated (`src/components/dashboard/demo-only.tsx`, `useSelectedClient`). **Currency:** amounts are stored in the ad account's native currency (real accounts span THB + JPY). `getClients()` derives `ClientRow.currency` from `ad_accounts` (NULL for demo clients → `DEFAULT_CURRENCY` USD); components format through `useCurrencyFormat()` (`src/hooks/use-currency-format.ts`), server code through `getClientCurrency(clientId)` + `formatCurrency(n, currency)`/`currencySymbol()` in `src/lib/format.ts`; `ReportData.currency` carries it into reports/exports/shared links. There is no FX conversion — cross-client sums mixing currencies are not meaningful.
- **Drizzle ORM is the DB layer** (`drizzle.config.ts`, `src/lib/db/schema.ts`, `src/lib/db/index.ts`). All DB reads (`src/lib/data/queries.ts`) and all API-route writes (`reports`, `reports/share`, `alerts`, `report-schedules`, `seed`) go through Drizzle. AdPulse tables are modeled via `adpulseSchema.table(...)` (the `adpulse` schema); the Atlas tables AdPulse reads are modeled read-only in `src/lib/db/atlas-schema.ts` (`public` schema). Auth is Clerk (`@clerk/nextjs`) — do **not** reintroduce supabase-js for anything.
- **camelCase ↔ snake_case boundary:** Drizzle models columns in camelCase, but the app (Zod schemas, mock data, the `*Row` types, the frontend, and the chat tools) speaks snake_case. Cross the boundary with `keysToSnake`/`keysToCamel` from `src/lib/db/case.ts` (shallow — nested JSON column values like `raw_payload`/`metrics_summary`/`reference_context` are passed through untouched). Reads map results with `keysToSnake`; writes map payloads with `keysToCamel`. `queries.ts` alternatively uses explicit aliased `select({ snake_case: table.camelColumn })` maps.
- **Schema changes go through a Drizzle SQL migration — never ad-hoc SQL run straight against the DB.** Every schema change is a new idempotent file `drizzle/NNNN_name.sql`, applied by the ledger-tracked runner `scripts/migrate.mjs`. The workflow for any schema change is:
  1. Write `drizzle/NNNN_name.sql` (next number after the highest existing file). **Only ever touch the `adpulse` schema** — Atlas owns `public` and manages it from the Atlas repo. Make it idempotent: `CREATE TABLE IF NOT EXISTS adpulse.…`, `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and `ADD CONSTRAINT` guarded by a `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname='…' AND conrelid='adpulse.<table>'::regclass) THEN … END IF; END $$;` block — see `drizzle/0000_shared_baseline.sql` for the pattern.
  2. Run `npm run db:migrate` (applies every pending file in ascending filename order, each in its own transaction, recording it in the `_migrations` ledger table). `npm run db:migrate:status` shows applied vs pending; `node scripts/migrate.mjs --mark-applied` records pending files as applied **without running them** (backfills the ledger on a DB whose schema already matches).
  3. Update **both** `src/lib/db/schema.ts` (Drizzle model — camelCase, keep its `index()`/`uniqueIndex()`/`check()` in sync with the SQL) **and** `src/lib/types/database.ts` (hand-written Row types) to match. These are hand-maintained mirrors of the DB; nothing generates them.
- **`drizzle/0000_shared_baseline.sql` is the full-schema baseline** (all 17 AdPulse tables, constraints, indexes, and RLS, everything inside the `adpulse` schema). It is fully idempotent: `db:migrate` against a target where the schema doesn't exist yet creates everything; a re-run no-ops. It has been applied to the `adpulse-dev` Neon branch; **`main` (Atlas production) has no `adpulse` schema yet** — run `db:migrate` against it before deploying. The ledger lives at `adpulse._migrations` (the runner creates it). The old standalone-project migration history is archived (never apply it) in `drizzle/archive-standalone/`. `psql`/`pg_dump`/Docker are not available in this environment; the runner uses the `postgres` package over `DATABASE_URL`.
- **Do NOT use or re-add the drizzle-kit generators.** `drizzle-kit pull`/`generate`/`migrate` are unreliable here — `pull` crashes on this project (`drizzle-kit@0.31.10`, `TypeError: Cannot read properties of undefined (reading 'replace')` while processing CHECK constraints, a drizzle-kit introspection bug). That is why `schema.ts` is hand-maintained and migrations are hand-written SQL. Only `db:studio` (read-only browsing) still uses drizzle-kit. If a future drizzle-kit upgrade fixes `pull`, review its output carefully before trusting it over the hand-written files.

## AI chat — do not "fix" the provider

`src/app/api/chat/route.ts` calls **OpenRouter** via raw `fetch` (model `google/gemini-3.7-flash`) with a manual tool-calling loop and SSE streaming. The `@ai-sdk/google` / `@google/generative-ai` deps are present but not used by the chat route. Do not refactor it onto the AI SDK without being asked.

## Seeding

`POST /api/seed` inserts 3 demo clients + 6 months of generated campaign data (including per-row `revenue`, plus `attribution_journeys` and `customer_cohorts` generated from the seeded rows so the blended-vs-reported ROAS, multi-touch attribution, and LTV:CAC stories reconcile). Pass `{ "force": true }` to drop and reseed. Requires an `agency_admin` session (i.e. an Atlas admin). The attribution mock data carries deliberate, demonstrable stories (see `src/lib/mock-data/attribution.ts`): ~35% platform over-attribution, Google last-touch-vs-first-touch credit divergence, and an LTV:CAC ranking that inverts short-window ROAS.

## Style & UI

- Tailwind v4, configured via CSS (`@import "tailwindcss"` in `src/app/globals.css`) — there is no `tailwind.config.js`.
- shadcn components use the **`base-nova`** style on `@base-ui/react` (not Radix), lucide icons. Config in `components.json`; aliases resolve to `@/components/ui`, `@/lib`, `@/hooks`.
- Path alias: `@/*` -> `./src/*`. TypeScript strict mode.
